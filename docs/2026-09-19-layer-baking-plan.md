# 2026-09-19 — 레이어 베이킹 계획 (옛 하드웨어 방식으로 되돌리기)

## 왜
옛 하드웨어는 같은 그림을 **텍스처 fetch(~30 ops/px)** 로 그렸고, 이 셰이더는 **매 픽셀 계산(~1000+ ops/px)**
한다. 실측: 4K에서 0.739 ms(RTX 5090) → 픽셀당 대략 1,000 ops 규모. 차이는 그림이 아니라 방식이다.

## 계획
1. **베이크 도구** ✅ `galaxy-work/work/bake_layers.py`
   아트에서 레이어 함수를 **그대로 추출**해(재구현 아님) 하네스로 4K PNG로 굽는다.
   `python bake_layers.py dust` → `outputs/bake-dust-bake-dust-4k.png` 생성 확인(밝은 픽셀 비율로 별먼지 검증).
   주의: 하네스가 `iTime`/`iResolution`을 스스로 선언하므로 셰이더에서 중복 선언하면 컴파일 실패.
2. **셰이더에 레이어 모드** (다음 단계)
   - `starDust(fragCoord, color)` 호출을 **채널 텍스처 샘플**로 교체(앱이 이미 `custom_shader_channel0..3` 지원)
   - `stars(...)` 4개 레이어는 **cloud 밀도장 의존**이라 그대로 굽으면 그림이 달라진다 →
     cloud 계산도 함께 추출해 굽거나, 굽는 시점의 대표값으로 근사(후자는 화질 변화 감수)
   - 함대·습격·행성은 **애니메이션·변주** 때문에 굽지 않는다(컬링/경계 최적화로 유지)
3. **검증**: 하네스 실측 + 굽힌 레이어와 원본의 픽셀 비교 → 설치·커밋

## 기대치(정직하게)
구울 수 있는 정적 몫은 실측상 `stars` 10% + `starDust` 14.8%(둘 다 교란 포함 과대값) 수준 →
추가 **−15~25%**, 이미 확보한 −25%와 합쳐 대략 **−40%**. 이벤트 장면(약 60%)은 굽기 불가.

## 대가
- 성운의 아주 느린 "숨쉬기"는 스크롤/패럴랙스로 근사(그림 미세 변화)
- 에셋 PNG 동봉 필요(리포에 포함)
- 별의 반짝임은 굽힌 밝기 위에 저렴한 변조로 근사

## 참고: 이미 확보한 최적화
화면공간 컬링(−19.5%) + 동적 루프 경계(−6.9%) = **−25%**, 전 단계 픽셀 동일.
